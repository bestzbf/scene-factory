# 微店监控数据集：全流程实现思路

本文自顶向下讲清这个项目在做什么、每一步为什么这么做、代码在哪里。数字都是实际跑出来的，不是估算。

---

## 一、目标

把 1,648 家便利店、12,289 张监控画面，变成 **1,648 个可编辑的 Blender 三维场景**：一家店一个场景，这家店所有摄像头一起输入。

为什么值得做：监控背景帧是成本极低的"免费重建信号"——同一个空间被 3–25 个不同角度拍到，且画面里没有人（已用两个模型筛过）。这比单张照片重建有信息量得多，又比激光扫描便宜得多。

难点不在"生成一个好看的图"，而在于：

1. **必须真的能对上照片**。相机位置、货架走向、收银台在哪，都要和画面一致，否则渲染出来的东西没有使用价值。
2. **必须可编辑**。输出是 `.blend`，每个货架、冷柜、收银机都是独立物体，能改、能导出。
3. **必须批量化且可续跑**。1,648 家店，任何一家失败不能拖垮整批，也不能重复付费。

---

## 二、整体架构：模型只读图，其余全由程序完成

这是整个设计最重要的一条界线。

```
照片（同一空间的 1–32 个视角）
   │  预处理：去时间戳水印 · 去畸变 · 统一缩放
   ▼
多模态模型 ── 一次请求 ──▶  library_layout_v1 布局 JSON
   │                        （房间尺寸、相机、灯光、
   │                          每个物体的类别/位置/尺寸/朝向/放在什么上面）
   ▼  本地程序，此后不再调用模型
选资产（类别 + 放置方式 + 尺寸）→ 自动挪位避让 → 支撑面/碰撞/边界检查
   │
   ▼
Blender 渲染每个机位 → scene.blend + rgb_view_XX.png + 标注 JSON
```

**为什么要这样切分。** 多模态模型擅长"看懂照片里有什么、大概在哪个方位"，但它不擅长两件事：给出精确到厘米的尺寸，以及保证几何自洽（两个物体不能穿模）。如果让模型直接写 Blender 脚本，它会写出一堆看起来合理、跑起来穿模、且不可复现的东西。

所以本项目的做法是：**让模型只做它擅长的那部分——输出一份受 JSON Schema 严格约束的布局**，具体用什么资产、放到哪个精确坐标、怎么避免碰撞，全部交给确定性程序。这样：

- 结果是可复现的（同样的布局 + 同样的资产库 = 同样的场景）
- 失败是可诊断的（不用去猜模型哪里想错了）
- 成本是可控的（每个场景恰好一次模型请求）

对应代码：`scene_factory/library_layout.py`（提示词、schema、校验）、`scene_factory/library_selection.py`（选资产与摆放）。

## 三、第一步：预处理（`tools/weidian_prep`）

原料是监控背景帧，三类问题必须先解决。

### 1. 去时间戳水印

监控画面右上角通常叠着日期时间和通道号。它会污染重建——模型会把它当成画面内容，色调匹配也会被它带偏。

做法分两条路：

- **粗白字**：按"白字形 + 黑描边"的像素特征定位，用形态学操作找出候选框。
- **细白字**：交给 macOS 自带的 Apple Vision OCR 离线识别，找到日期/时间所在的那一行，取它的包围盒。

识别出来之后**只修补笔画像素**，不是贴一块色块。这样即使水印压到商品上，修补后也不会留下明显的补丁。

效果：**98.4%** 的画面去掉了时间戳。

### 2. 去畸变

广角监控镜头普遍有桶形畸变。场景工厂的相机是理想针孔模型，畸变不校正，"相机估计"和"渲染对位"就会系统性偏掉。

做法用单参数除法模型，关键是**怎么估计参数**：

> 把被商品打断的同一条货架边当成一条直线，找让这些碎片最直的参数。

这不是靠猜，是有明确的目标函数。为了保证可靠，还会把线段随机分成两半各估一次，两次结果一致才采用；单张图证据不足时，借用同店同分辨率摄像头的中位数或合并估计。

效果：**88.8%** 做了去畸变。

### 3. 统一缩放

原图分辨率混杂（1280×720、1920×1080、720×576 都有）。统一缩到长边 1280，既省 token，也让各视角一致。

### 输出

每家店一个目录，外加：

- `groups.json` — 场景 ID 就是店铺号，可直接交给 `scene-factory run --groups`
- `manifest.json` — 每张图的来源哈希、水印框位置、畸变参数
- `qa/` — 前后对比图，用来人工抽查

全量 1,648 家约 40 分钟（多进程），**0 家失败**。有一张源图在 COS 上就是截断的，跳过并记录。

## 四、第二步：资产库

这是整个项目真正的瓶颈，也是投入最多的部分。

### 为什么资产库是瓶颈

`library_layout_v1` 有一条硬规则：**模型识别出的物体，只要有一个在资产库里配不上，整个场景就失败**，并在报告里写明是哪个物体、为什么配不上。程序不会拿方盒子凑数。

这条规则是对的（否则出来的是缺了冷柜、收银台的残缺场景），代价是资产库必须覆盖模型会提到的所有类别。

第一次试点的结果很说明问题：12 家店，模型 12/12 成功返回布局，但**出图 0 家**——598 个物体里只有 165 个（28%）能配上资产。

### 配不上的两种原因

1. **库里根本没有这一类**（冷柜、收银台、收银机、商品）
2. **库里有这一类，但尺寸配不上**——资产只能整体等比缩放到 0.8–1.25 倍，三个方向一起缩放。便利店货架是长 1.5–2 m、高 1.6 m 的矮长架，库里 8 个货架多是窄高的家用书架（1.0×0.26×2.08 m），等比缩放后对不上。

### 解法：按模型实际要求的尺寸造资产

关键决定：**不做"通用资产"，而是按模型真实要求的尺寸批量生成**。

因为选资产的规则是"类别 + 放置方式 + 等比缩放 0.8–1.25 且每轴误差 ≤25%"。如果直接按模型要求的精确尺寸造一件，那么这件资产 **必然**能通过筛选——剩下的问题只有"形状像不像"。

于是有了 `tools/asset_library/retail/plan_topup.py`：

- 输入：所有运行中"配不上"的物体，按 (类别, 放置方式, 精确尺寸) 聚合
- 每个类别映射到 `build_retail_asset.py` 里的一个程序化 archetype（货架、冷柜、纸箱、麻袋、电扇…共 30 多个）
- 形状不对时按规则改写，例如：圆柱类 archetype 不能拉伸成长条形方盒（生成器会拒绝 0.75–1.34 以外的逐轴缩放），所以长条形的"托盘"改用方盒；**托盘必须做成有顶面的实体**，因为模型要在上面放茶壶，开口的盒子测不出支撑面

资产用 Blender 程序化生成，商品用无品牌的彩色包装块表示（纹理图集），不下载任何模型，也不调用任何 API。

### 四轮演进

| 版本 | 资产 | 类别 | 怎么来的 |
| --- | --- | --- | --- |
| 20261029 | 583 | 136 | 原始库（Tripo 生成 + Poly Haven） |
| 20261030 | 4,106 | 199 | 合并 3,523 件程序化零售资产 |
| 20261031 | 5,573 | 461 | 补 1,467 件（第一轮缺口，737 个规格） |
| 20261032 | 5,779 | 554 | 补 206 件（第二轮缺口，139 类） |

**效果实测**（对同一批 215 家卡住的店做纯选资产测试，不渲染、不调模型）：

| 资产库 | 可选中的店 |
| --- | --- |
| 20261030 | 0 / 215 |
| 20261031 | 148 / 215（69%） |
| 20261032 | 160 / 215（74%） |

这是最直接的证据：补资产确实在解决问题，而且不花钱。

### 一个副作用

20261032 有 554 个类别，**超过模型提示词的 256 类上限**。`library_layout.catalog_context` 在类别超限时会明确报错而不是静默截断（这个设计是对的）。所以大库只能用于离线重渲——选资产是逐个物体进行的，不受提示词限制。

想让模型调用也用上大库，需要提高这个上限，或者按实际需求裁剪类别。我做了个 256 类的裁剪版（`tools/asset_library/scope_library.py`），但实测可选率只有 96/215——因为裁掉的恰恰是模型点名要的长尾类别。所以**这个裁剪版不划算**，真正的解法是提高上限。

## 五、第三步：布局生成

### 模型做什么

每个场景一次请求，把这家店所有摄像头一起发过去（最多 32 张）。模型返回一份严格 JSON：

- 房间：宽、深、高、地板/墙/天花板颜色
- 相机：每个视角的位置、朝向、焦距
- 灯光：位置、类型、能量、尺寸
- 物体：类别、位置、目标尺寸、朝向、**放在什么上面**（`support_id`）

`support_id` 是关键设计：模型不只要说"这里有个收银机"，还要说"它放在收银台上"。这样程序能算出支撑关系，检查悬空。

### 为什么一个场景只请求一次

- **成本可控**：每个场景恰好一个请求的预算，超了就停
- **不会重复付费**：请求发出后如果结果不确定，程序禁止自动重发
- **失败可诊断**：一次失败就是一个明确的错误码

### 失败保护

`batch_budget`（`scene_factory/batch_guard.py`）：

- 上限：最多 N 次请求、N 输出 token、N 总 token
- 熔断：连续 5 次服务端失败就停止；返回 401/402/403 立即停止
- 磁盘：剩余空间低于阈值时不再开始新场景
- **中断即熔断**：如果一次请求已发出但结果未知，账本留一条"预留"，阻止自动续跑

最后这条在实战里救过一次：网络抖动导致 5 次连败熔断，账本里有 2 条"已预留、结果未知"的记录，`--resume-batch` 因此拒绝续跑。这不是 bug——它防止了重复扣费。

## 六、第四步：选资产与摆放

这一步完全确定性，`scene_factory/library_selection.py`。

### 选资产

对每个物体，按 (类别, 放置方式) 找候选，要求能**等比缩放**到目标尺寸，缩放系数在 0.8–1.25 之间，每轴误差 ≤25%。

有多个候选时优先挑这个场景里还没用过的，避免一个货架重复出现十次。

### 自动挪位（settle）

模型估计的位置常有几厘米到几十厘米的重叠。开启 settle 后：

- 重叠或悬空的物体，在 0.5 m 范围内找最近的空位
- 台面上的小物跟着支撑它的物体一起移动
- 每次移动都记录在报告里

### 大件保护

占地 ≥0.5 m²，或高 ≥1.2 m 且占地 ≥0.2 m² 的落地物体算大件（收银台、冷柜、货架）。

大件**先占位置，可以挪到 1.0 m，而且永不省略**——放不下就整个场景失败，而不是悄悄丢掉一个冷柜。

这里修过一个真实的 bug：判断大件时原本只用"选中资产的尺寸"，导致模型要求 1.25 m 宽、实际选到 1.20 m 宽的柜台被判成小件，然后被省略了。现在**按模型要求的尺寸和选中资产的尺寸分别判断，任意一个达标就算大件**。加了回归测试。

### 省略上限

实在放不下的小物可以省略，但每个场景最多省略 10%，超过就整个场景失败。

## 七、第五步：渲染

每个机位渲染一张，输出：

- `scene.blend` — 可编辑工程
- `rgb_view_XX.png` — 渲染图
- `annotations_view_XX.json` — 标注（每个物体的类别、边界框、可见性）
- `result.json` — 结果状态

批量配置是 1600 px / 128 采样；demo 用 1920 px / 256 采样。

关于色调：`tone-match reference` 会把渲染和原图做一次曝光校准，每个场景求一个换算到 EV 的修正量。实测大部分场景修正量在 ±0.75 EV 以内。

### Demo 参数是怎么定下来的

调色改不了结构差异，这一点是实测出来的：

| 尝试 | 结果 |
| --- | --- |
| 提高环境光 | 顺带修掉一个真 bug：覆盖写到了 `render.world_strength`，而渲染器读的是 `base_scene.lighting.world_strength`，所以这个参数一直是无效的。修好后天花板不再是全黑 |
| 强制统一焦距 32 / 40 / 50 mm | 部分店变好、部分店被拉成特写，平均更差，**已放弃** |
| 从照片采样地板/墙/天花板颜色 | 测试机位亮度误差 15.9 → 4.2，**保留** |
| AgX Punchy look | 饱和度更接近，**保留** |

最终 demo 用 `--world 0.55 --ev 0.1 --from-photo floor,wall,ceiling --look 'AgX - Punchy'`。

**真正的差距在布局。** 对 494 家有渲染结果的店做了结构对齐打分（梯度幅值相关 + 梯度方向一致度），最高的也只有 0.10。也就是说模型给出的房间尺寸、相机位姿、货架摆位和照片本身对不上，靠曝光、焦距、色调都修不回来。所以 demo 选的是结构分最高、物体最多的三家店，而不是硬调参数。

## 八、实际跑出来的结果

### 出图率

| 批次 | 提交 | 出图 | 说明 |
| --- | --- | --- | --- |
| OpenAI 官方（10-30） | 88 | 8 | 账户余额耗尽，触发熔断 |
| 微店网关 第一批 | 325 | 56 | 网络抖动熔断 |
| 微店网关 过渡批 | 59 | 7 | 换配置前的一次短续跑 |
| 卡住店铺补跑 | 28 | 4 | 用了一次单独预算 |
| 微店网关 第二批 | 1,205 | 281 | 跑完 |
| **模型批次合计** | **1,705** | **356** | |
| 离线重渲（不调模型） | 163 | 163 | 用已付费布局 + 新资产库 |

**最终：519 家店出图，约占 31%，约 4,100 个渲染机位。**（同一家店在多批里可能被提交两次，519 是去重后的店数。）

### 失败原因（未出图的 1,129 家）

| 原因 | 家数 | 占比 |
| --- | --- | --- |
| 缺资产 | 724 | 64% |
| 模型调用失败（网络/格式/熔断） | 380 | 34% |
| 渲染失败 | 25 | 2% |

**缺资产仍是主因**，而这是最有希望解决的一类——这 724 家都有付费布局（`initial_layout.json`），补完资产后可以离线重渲，不再调用模型。

### 花费

44.4M token / 1,608 次有效请求，平均每家店约 27,600 token。

### 一个质量问题

519 家出图的店里，**25 家（5%）**大部分机位渲染出来是灰色空白，另有 41 家有个别机位如此。

原因查清了：**模型把相机放到了天花板以上**。便利店顶高 3.0–3.2 m，模型却把部分相机放在 4–6 m——这些相机拍到的是天花板上方的空腔。

| 类别 | 店数 | 机位 | 相机在天花板以上 |
| --- | --- | --- | --- |
| 空白严重 | 25 | 125 | 118（**94%**） |
| 部分空白 | 30 | 185 | 26（14%） |
| 正常 | 301 | 2,076 | 55（3%） |

正常店只有 3%，说明这是少数场景的异常，不是系统性问题。修法很直接：渲染前把相机夹到天花板以下（`render_demo.py --clamp-cameras`）。

## 九、还差什么

按影响排序：

1. **缺资产的 724 家**（最有价值）。已经统计清楚：523 个缺失类别，其中 86 类是"库里有但尺寸/放置配不上"——这 86 类卡了大部分店（sack 111 家、glass_door_refrigerator 111 家、wire_display_rack 104 家、shelf 104 家、cardboard_box 75 家）。这类问题只需扩大现有资产的尺寸范围或增加放置方式，不用重新建模。
2. **口径问题**：提高模型提示词的类别上限，让 554 类的大库能直接用于模型调用，而不是只能离线渲染。
3. **相机夹取**：把 `--clamp-cameras` 的逻辑放进正式批次，消掉那 5% 的空白机位。
4. **渲染质量**：商品仍是规则彩色块，光照偏平。要更接近照片，需要真实商品模型或更好的材质/光照估计。

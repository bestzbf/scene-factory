# Scene Factory 0.3.39 批量生产

## 可直接使用的流程

每张独立照片生成一个场景；同一个子文件夹的 1–16 张照片共同生成一个场景。模型通过 API 负责分阶段照片分析、多视角联合理解、原图与渲染对比、修正和最终评分。固定本地程序校验 JSON 并操作 Blender，不需要 Codex CLI，不执行模型返回的代码。

生产配置默认开启验收，`batch.max_repairs=2` 是技术修复与视觉修复共享的候选修改次数：最多初始候选加两次修改。若一次技术修复、一次视觉修复已用尽预算，最后候选仍必须重新渲染和独立审核。关闭视觉验收时仍可设置 `max_repairs`，此时只对阻断性本地预检错误运行有界技术修复；成功渲染仍标为 `generated_unreviewed`，不能进入正式数据集。`run` 保留所有任务供排查；`export` 只发布通过最新一轮验收、输入和产物完整性验证的场景。合格判定是模型启发式评分与技术检查，不是测量级几何或照片级相似度保证。

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install .
scene-factory init --directory ./production --profile bigmodel-production
# 可选：仅对高置信度构件减少细节阶段的重复图片输入
scene-factory init --directory ./production-economy --profile bigmodel-production-cost-saving
```

在本机设置 `BIGMODEL_API_KEY`，不要将密钥写入配置、源码或聊天。GLM 模板使用 `https://open.bigmodel.cn/api/paas/v4`、`glm-5.3-flash`。三个模型角色可以各自更换模型、兼容协议、URL 和密钥环境变量。使用其他服务时选择 `openai-compatible` 模板并填写实际地址；开启 `batch.no_review=false` 和 `max_repairs`，推荐沿用 GLM 模板的分阶段设置。

```text
production/
  factory.json
  photos/
    corridor.jpg                  # 一个场景
    dorm.jpg                      # 一个场景
    computer_lab/
      front.jpg                   # 同一场景的两个方向
      back.jpg
```

`init` 创建的空示例文件夹可以删除或改名。所有子目录里的照片均属于该子目录对应的一个场景，不会逐文件再拆分。

```sh
scene-factory doctor --config ./production/factory.json
scene-factory probe --config ./production/factory.json
scene-factory run --config ./production/factory.json --input-dir ./production/photos --output-dir ./production/output --dry-run
scene-factory run --config ./production/factory.json --input-dir ./production/photos --output-dir ./production/output
scene-factory status ./production/output
scene-factory usage ./production/output
scene-factory report ./production/output
scene-factory export ./production/output --destination ./production/dataset-v1
```

`doctor` 离线检查配置、凭据是否已配置、Blender 位置、Python 依赖，以及所配置资产库的结构/文件哈希。它不证明模型支持多图、不启动 Blender 渲染。`--dry-run` 只校验配置/分组和输出路径，不检查全部图片内容或联网。`probe` 会产生真实 API 消耗；用于小图和 JSON 能力测试。`run` 会持续消耗模型额度并启动实际 Blender。`status`、`usage`、`report`、`export` 均不调用模型。

## 可选：一次生成与明确的承托摆放

当前源码提供 `bigmodel-single-pass-anchored` 模板：

```sh
scene-factory init --directory ./single-pass --profile bigmodel-single-pass-anchored
```

每个场景只允许一次 GLM-5.3-Flash（low）请求，输出完整 JSON 后本地校验、渲染。它关闭视觉复审、模型修正、验证重试及传输重试，保留原图分辨率，输出上限 12,288 token。不要先执行 `probe` 再把它的消耗算入“一次生成”；`probe` 是独立付费请求。一次请求或输出上限不保证完整响应，失败仍保留已发生的用量。

`pipeline.scene_wire_format=anchored_parts_v1` 保留 typed-parts 几何编码，并要求基础物体声明摆放语义：`floor` 提供 XY，程序计算底部 Z=0；`on_top` 指定准确支撑物实例和 XY，程序按支撑物底部加高度及 0–3 cm 间隙计算底部 Z；`world` 提供明确的底面中心 XYZ，用于悬挂、抬高或其他独立高度。它不会根据类别把物体移到地板，也不会自动调整 XY。

`on_top` 仅支持内置 desk、table、cabinet、shelf、box 的外侧平顶，不能指代内部层板、椅座、床垫或自定义曲面。重复组必须引用 `id__i_j` 的准确实例；重复子物体可以共享一个准确支撑实例，但程序会检查每个展开副本的底面中心是否位于旋转后的承托范围（2 cm 容差），不保证整个底面均被支撑或不存在其他碰撞。承托图不得成环；承托物可先于或后于子物体输出。省略基础地板时不能声明 `floor`。初版拒绝与外部资产库一起配置，因为外部模型的锚点和实际接触面尚未验证。

原始 wire 响应单独保留，存储和 Blender 使用原有 canonical V3；`analysis_provenance.json` 记录格式、实现哈希和逐实例摆放计算。已完成响应在严格核对请求身份后续跑复用，承托校验失败不会隐式追加模型调用。其他配置的默认格式仍为 canonical；升级代码或切换格式应使用新输出目录。

该模板解决底部/中心高度的表达歧义，不证明模型的照片理解、尺寸、支撑选择、布局或材质正确。2026-10-27 的单张办公室 GLM 实测为一次请求、19,827 tokens、约 219 秒分析；曾因重复组材质别名的本地验证问题失败，修复后用原响应完成渲染，没有再次调用模型。图像仍缺少大量细节，布局和透视偏差明显；这不是还原质量或 token 节省的成功证明。成功输出仍为 `generated_unreviewed`，不能直接进入正式数据集。现有 wheel 不自动获得源码中的新模板，使用前需安装当前源码。

## 实验性：重复构件一次生成

`bigmodel-single-pass-patterns` 沿用单次请求、原图分辨率、low、零复审/修正/重试和每场景 1 次请求预算：

```sh
scene-factory init --directory ./pattern-trial --profile bigmodel-single-pass-patterns
```

它使用 `pipeline.scene_wire_format=anchored_patterns_v1`。模型在每个 custom_objects 组内输出 `parts` 原型和 `part_arrays`，例如 `{"part_indices":[0],"count":[1,1,4],"spacing":[0,0,0.3]}` 表示第 0 个原型沿组的局部 Z 每隔 0.3 米重复，共 4 个（包含原位置）。没有重复时填 `part_arrays=[]`。原型索引只能归属一个阵列；所有字段和次数均需明确，程序不推断阵列、不补充杂物、不随机改变材质。

按原型顺序，每个原型在 X 外层/Y 中层/Z 内层顺序展开。位移加到 part.position，在部件旋转之后、组旋转之前的组局部坐标中；顶点、曲线点、形状、旋转、材质和布料参数均不改变。模型需要保证原型间差异表达完整，不能将不完全相同的物体强行阵列化。

解码器在分配展开对象前检查每组 100、全场景 800 parts 和全部拓扑预算，拒绝重复/未知索引、零间距重复轴、非有限值、越界坐标及未知引用。之后仍走原有 canonical V3 规范化、支撑与身份校验、本地几何预检及 Blender 渲染，不放宽验收。`analysis_provenance.json` 附有 `pattern_report`：每个最终 part 对应的源 part 索引、array 索引与 XYZ 重复索引；原始响应单独保留。代码、schema、提示及相关依赖进入指纹；升级或改模式请用新输出目录。

新模式使用专门的提示，不叠加旧版“所有 part 字段都必填”与 typed 字段例外。旧模式提示保持不变，已完成响应仍可按原身份恢复。它能以较短 JSON 表达准确重复，但尚未进行同模型付费对照，不能声称实际 token 节省、速度提高或照片还原改善。已有本地测试证明 schema、恢复、严格预算与 Blender 展开语义；合成构件相等不代表照片理解正确。模板不自动启用到现有生产配置，结果仍为 `generated_unreviewed`。

## 渲染前自动修复与光照诊断

Blender 构建后先检查实际几何：严重越界的家具、相机与保留墙体的碰撞、基础窗背后的不透明保留墙、覆盖窗洞的大面积低透射照片贴图层。报告包含对象、包围盒、覆盖率以及当前 `scene_bundle.json` 的 SHA256。只有当前构建产生的阻断报告会启动技术修复，普通渲染崩溃、超时、过期报告不会被当作可修复几何问题。

生产配置下，技术修复 API 接收原照片、当前 JSON、检测证据与资产选择记录，输出受约束的 JSON 修改。程序逐项校验后在新的 `iteration_*` 中重建，重跑检查，再渲染并进行独立原图/渲染审核。不存在按房型硬编码移床、统一提高灯光功率或跳过最终验收的路径。`technical_history.json` 与逐轮 `technical_repair_provenance.json` 留存完整证据；恢复运行时验证输入、报告和修复产物哈希。

基础窗玻璃采用折射外观与透明阴影近似，使外部灯光可以进入室内；这是避免昂贵折射焦散的渲染近似。曝光校准后记录 3×3 分区亮度残差，审核/修复 API 可据此判断局部明暗与全局曝光问题。该数值受构图和材质影响，是诊断线索，不是照片还原分数。检测覆盖明确列出的情况，无法穷尽所有窗体或复杂材质的遮挡。

API 因 token 上限截断输出时不接受残缺 JSON，在现有总超时和验证重试上限内要求更简洁的完整输出。GLM 模板的修复推理强度设为 `low`，分析仍为 `high`，以避免修复请求把额度全部用于推理；这不是还原质量保证。预算耗尽、修复无变化或 API 失败的场景会被隔离，其他场景继续。

自动技术修复需要配置模型 API、正的修改预算且采用 `pipeline.repair_mode=typed`。关闭视觉验收时仍可修复阻断性本地预检错误；成功渲染标为 `generated_unreviewed`，并且不能导出为正式数据集。启用视觉验收时，技术修复与视觉修复共用同一修改预算。

## 连续运行、恢复和追加照片

- 场景同时处理量由 `batch.workers` 控制，1–8；只提交相应数量的任务到执行器，不为所有场景预先创建 future。
- 同一批次进程内的所有场景、规划、细节、审核和修正请求共用 `batch.api_workers` 上限，1–32，默认 2。排队时间计入请求超时。模型服务限流可将它降为 1；`detail_workers` 不会突破此上限。多个独立进程分别计数。
- API 并发排队每次最多等待 0.1 秒后检查停止事件，取得名额后再检查一次。排队取消不会读取密钥、编码图片、发送请求或占用预算预约；已发出的请求仍遵守原有请求超时和结果不明时禁止自动重放的规则。此处 0.1 秒是等待间隔，不是整批退出时间保证。
- 模型配置可选 `rate_limit` 按供应商端点预约 RPM/TPM，详见 [TOKEN_BUDGETS.md](TOKEN_BUDGETS.md)。同一账本根目录的 `provider_limits.sqlite3` 保留最近一分钟的预约；同端点各角色共用较严格的正额度，每次 HTTP 重试都计入。排队计入请求超时并响应停止事件。默认不启用；机器之间不共享配额，TPM 的图片和输入 token 预约需按服务商规则设置，不能据此保证不触发服务商限流。
- 实际运行 1,000 个或更多场景前，必须在配置中为整批设置正数 `batch_budget.max_requests`、`max_output_tokens`、`max_reported_tokens`；否则在 provider/Blender 预检和任何模型请求之前停止。`--dry-run` 不要求预算；大批次只输出计数和前 20 个场景预览，并列出正式运行缺少的上限，不会打印整份路径清单。额度依赖服务商账户和期望的最大支出，由操作者配置。默认账本只覆盖一个输出目录；设置 `batch.shared_ledger_dir` 后，同一台机器上位于共享根目录内的多个分片输出可共用预算和限流账本。所有分片须使用相同共享目录及预算/限流配置，并位于可靠的本机 SQLite 文件系统；不支持跨机器共享。
- 批次停止事件若在连接建立期间到达，会在 POST 前拦截并退还可证明未发送的预约。`probe` 临时输出目录也会启用相同配额预约；直接调用 Python API 时仍需显式建立配额 session。
- 多视角 staged 分析默认每个细节调用都携带全部原图。质量优先模板保持此行为；`bigmodel-production-cost-saving` 是显式省输入配置，会根据规划阶段为每个构件声明的证据视角减少重复图片输入，规划阶段仍接收所有原图。仅当构件已观测且 `evidence_confidence` 达到配置门槛才裁减视角；该配置将门槛设为 0.90（通用默认值为 0.75），未观测、置信度较低或证据不明时回退为所有原图。它还启用 `native_sparse_parts_v1`，用稀疏几何记录替代未使用的空数组；完整数值与拓扑保留，解码后仍经过完整验证。离线回放五个历史 GLM 细节响应（132 个部件），prompt、schema 和响应合计 UTF-8 字节减少 3.83%；字节不是 token，且没有测量该编码下的模型视觉等价。照片纹理来源视角会保留，原始图片分辨率不变。证据映射由规划模型给出，置信度阈值未经校准；若模型漏报有用视角，细节阶段可能损失跨视角信息。图片数减少和稀疏编码都不等于已确认节省相同比例 token，也不证明视觉质量等价；切换正式数据集前应检查 provenance 中每组 `input_view_ids` 并做真实模型质量回归。
- 当细节计划表编码连同说明短于原计划时，细节请求只省略非目标构件的 `evidence_view_ids` 和 `evidence_confidence`；当前构件的字段、所有构件的空间/支撑/材料/构造信息及完整本地计划均保留。该投影不改缓存计划或最终场景数据；小计划会自动回退到完整计划文本。它只减少重复文本，不构成 token 或费用测量，也没有单独的视觉质量等价证明。
- `batch.render_workers` 控制同一批次进程内的 Blender 同时运行数，1–8，默认 1；也可通过底层入口的 `--render-workers` 设置。排队中的渲染响应中断，运行中的 Blender 完成当前调用；`progress.json` 的 `render_queue_seconds` 单独记录等待时间，`render_timeout` 仍只约束实际 Blender 调用。提高并发前需测量 CPU、内存和显存，多个进程不会自动分配不同 GPU，也不保证提速。不同批次进程不共享此上限。当前版本不是多机任务调度器；多进程或多机运行请按不同输出目录分片，并自行控制机器负载。
- `batch.min_free_disk_bytes` 可设置输出卷的最低可用字节数，默认 `0`（关闭）。启用后，程序会在启动初始化、入队前以及 worker 开始新场景前检查余量；低于阈值或无法读取磁盘状态时进入 `paused_disk_space`，退出码为 `75`，已提交结果保留，未入队/未开始的场景保持 `pending`，恢复空间后可用同一命令续跑。已入队且正在运行的 API/Blender 工作不会因这个闸门被取消，可能继续把可用空间降到阈值以下；该保护只控制新场景准入，不预估单场景最终大小，也不替代分阶段试产。启动前置检查不会改写已有 `summary.json`、`accepted.json` 或 `groups.json`。
- 失败按场景隔离，其他任务继续；API 对网络/429/服务端错误的重试次数由模型配置 `max_retries` 控制。JSON 格式校验重试有独立上限；几何/透光技术修复与视觉修复共享 `max_repairs` 上限，不会无限返修。
- 重新运行相同 `run` 命令可恢复失败/中断任务，复用已提交且哈希一致的模型阶段与渲染。已完成且未变的场景不重复调用模型或渲染。`needs_review` 是本轮额度内未通过验收的终态，不会在每次续跑时反复花费；更换配置、修正上限或代码后使用新输出目录。
- 加入新照片或新的场景文件夹后再次执行原命令。ID 根据相对路径稳定生成；历史分组、汇总和合格索引会保留。不要重命名已有照片、改变已有场景的分组或修改正在处理的文件。
- 首次 Ctrl-C 会停止调度，运行中的 API/Blender 调用完成当前步骤后退出，并保留缓存；退出码为 130。硬退出后可重跑；已经完整保存的整场景 API 响应在核对 prompt、schema、模型配置、原图和原始响应哈希后只读复用，再执行本地规范化。未收到完整响应、缺失审计或请求身份不一致时拒绝自动重放；不能通过删除账本来继续。
- 同一输出目录由操作系统文件锁保护。正常退出或进程崩溃会释放锁；保留的 `.batch.lock` / `.process.lock` 文件本身不代表仍运行，不需要删除。旧版无法确认归属的 `.lock` 不会自动删除。请使用本机磁盘；网络文件系统必须自行提供可靠的同等锁语义。
- 共享账本的 pending 预约绑定到本次调用的唯一 owner generation，并由该 generation 的操作系统锁证明仍在运行。新进程重新取得同一分片目录锁不会继承旧请求身份；崩溃留下的旧预约和旧版无 owner 记录保守阻止自动续跑，原请求数与 usage 保留。
- 整场景 API 完成但本地语义校验或 provenance 提交失败时，续跑只读复用经完整身份及 transport/hash 校验的原响应；语义失败仍会被拒绝，不会隐式追加修正调用。明确被 HTTP 拒绝或可证实未发送的失败，在允许继续且预算足够时使用独立的 `_retry_N` 审计，不覆盖旧 prompt、raw 或 usage。 失败审计的请求次数与 transport 证据必须一致；空 transport 或互相矛盾的“未发送/已收到响应”记录不能触发新请求。显式指定恢复源时，已有场景记录但响应文件缺失也会停止，不按缓存未命中重新付费。
- 输入、模型配置、代码和资产文件均有指纹。变化时拒绝套用旧验收；原图、原资产应保留到本批次完成并导出。升级程序或更改处理配置后请使用新的 output，保留旧结果。

输出目录中的 `summary.json`、`accepted.json` 在启动和退出时生成兼容快照；运行期间逐条追加 `batch_events.jsonl`，并原子更新小型 `run_state.json` 与逐场景 `progress.json`。`status` 与 `report` 合并同一 run_id 的增量事件；事件不是验收证据，导出仍检查逐场景提交和文件哈希。`status` 输出最后一次快照，不是心跳检测；进程硬退出后显示 running 也可直接重跑。`status --verify` 进一步复核已接受记录的文件和输入哈希，较大资产库可能耗时。

`usage` 汇总已保存的 provider/model 调用、HTTP 尝试、失败数和服务端报告的 token；逐 HTTP 尝试求和，不重复累加最后一次的使用量。缺失回包和服务商计费调整不可推断，报告不是完整账单或费用承诺。

`usage` 报告同时附带 `payload_metrics`，汇总本地记录的请求 JSON、输入图源文件/Base64、HTTP 响应和提取输出的 UTF-8 字节数；每个 `.api.json` 还保留逐图像素尺寸。它们只用于离线请求回放和载荷对比，不是 provider token、图像 token 或费用估计；真实 token 仍以服务端回传的 `usage` 为准。

## 正式数据集与不合格结果

`accepted` 要求当前最终渲染对应的全部视角经过审核，realism≥90、其余维度≥85；没有 major/blocking 问题、可见资产缺口或技术警告；每视角至少 1280×720（横竖均可），且至少 64 samples。细长比例图片即使长边为 1600，短边也可能不足 720，请提高 `render.max_edge`。预览资产和未审核输出不进入正式数据集。

`needs_review` 表示本轮审核未通过或返修上限已耗尽；`generated_unreviewed` 表示关闭了审核；`failed` / `review_failed` 表示流程或审核/修正失败。这些目录保留 Blender 文件和证据，但 `export` 不会发布它们。返回码 0 表示任务没有流程异常，不表示所有照片均通过视觉验收。

`export` 从实际逐场景结果读取候选，重新验证最后一轮、审核来源、审核输入、渲染输出与文件 SHA256，不依赖手写的 `accepted.json`。篡改或缺失的合格产物会使导出失败。导出期间锁定源批次与目标，目标锁文件保留并可在进程退出后复用。目标必须是新目录，先在旁边暂存，全部成功后通过操作系统的禁止覆盖重命名原子发布；不会覆盖已有数据集。没有通过的场景时不会假造合格场景。

命令行默认只打印场景数、视角数和完整清单路径；完整逐场景文件清单始终写入数据集的 `dataset_manifest.json`。需要同时在标准输出返回所有条目时使用 `export --full-result`。Python API 仍默认返回完整条目；万级调用建议设置 `include_scene_entries=False`，避免保留整份清单的额外内存。

导出包含可编辑且贴图已打包的 `.blend`、各视角渲染/标注、原图、可搬迁的场景描述和裁剪贴图，以及必要的资产子集和验收证据。manifest 记录逐文件哈希；API 原始响应、prompt、配置和运行日志不作为正式数据集内容。源任务目录保留原始证据；导出的审核说明改写为本地相对路径，另记录原审核、来源和渲染状态文件的哈希用于追溯，明确标记路径改写，不把导出版本当成原审核输入。源文件哈希验证不是数字签名或防恶意伪造机制。

## 接入大量资产

```sh
scene-factory init --directory ./production-assets --profile bigmodel-auto-assets
```

将合格目录放到 `production-assets/assets/asset_catalog.json`，或修改配置相对路径。该模板开启自动绑定，无需每场景写绑定文件。几何和材质只能按兼容规则组合；同组照片共用同一绑定。还原任务默认 `selection.diversity=false` 先按类别和尺寸选；做数据增广时再设 true 以偏好多样组合。

当前自动绑定仅支持规则可证实的地面基类物体，采用均匀缩放、底面对齐和严格生产清单。自定义组合、桌面小物或不兼容的候选保留程序建模并记录 fallback，不会强行套错资产。没有实现图片外观向量检索、深度估计、精确网格碰撞或在线生成任意三维资产。全目录内容完整性检查在大型库上有 I/O 成本，建议为生产批次发布不可变的已筛选库；当前不是万级资产检索性能的完成证明。

资产规范见 [ASSET_PRODUCTION_STANDARD_V1.md](ASSET_PRODUCTION_STANDARD_V1.md)，调用说明见 [ASSET_LIBRARY.md](ASSET_LIBRARY.md)，HARMONY 参考分析见 [HARMONY_WORKFLOW.md](HARMONY_WORKFLOW.md)。批量稳定性、资产可调用性、照片还原质量是不同验证项。大规模投产前用自己的代表性室内图评估通过率、平均返修次数、耗时和 token；自动验收是筛选工具，不能保证每个输入都能成功还原。

## 0.3.5 真实执行后的外观校验

`render.tone_match=reference` 现在启用实际 Cycles 预览的共享灯光/环境/曝光有限搜索：最多 15 组灯光候选，全部视角共用一组物理参数，至少 2% 改善且各视角不明显退步才采用。记录原始请求和实际应用功率；最终 PNG 另行计量，模型审核仍独立决定是否达标。

视觉修正先渲染、审核，再通过 `candidate_selection.json` 比较每视角分数、主要缺陷和最终图片区域亮度。显著退步或无有效改善会保留前一最佳候选，下一次修改从它继续。失败尝试用 `failed_iteration` 标明；保留最佳不意味着通过验收，失败状态仍不可导出。

支持显式基础资产材质槽绑定、带真实褶皱的参数化布帘、窗外可见内容与采光分离。参见 [材质和布帘契约](MATERIAL_CLOTH_CONTRACT.md)、[窗外契约](EXTERIOR_CONTEXT_CONTRACT.md)、[灯光拟合契约](LIGHTING_FIT_CONTRACT.md)。窗外是有视差限制的共享 2.5D 外景平面；布帘没有仿真；内置资产以独立材质副本显式标记源槽位角色，外部资产未声明角色时仍可能使用启发式。源角色与目标材质的物理性质无关，例如 shelf 的 body 可绑定金属材质，但不能据此假设 shelf 有 metal 源槽位。所有能力需要原图支持和最终审核，不能据此保证任意照片能被高质量还原。

## 0.3.5 修正前置校验

材质选择器先对未变动基础资产的实际 source_material_key 等槽位证据校验，错误在同一 API 校验循环内重试，避免占用一轮 Blender 候选预算。每个视角的逐部件投影、支撑接触和越界警告也发送给修正模型，并绑定完整 annotations 文件哈希。投影只判断视锥入画，不证明无遮挡；详见 [逐部件投影契约](CUSTOM_PART_PROJECTION_CONTRACT.md)。

## 0.3.6 光照严重残余保护

共享灯光拟合目标加入最差三分之一区域的平方误差，避免多数暗区掩盖少数严重偏暗/偏亮区域。报告记录目标版本、严重残余和需要检查非功率因素的标记，修正模型会据此检查构图、光源方向/尺寸、通光和反射率。此项改善误差权衡，不能替代照片级外观重建；不同目标版本的损失数值不可直接比较。


## 万级任务的已验证范围（0.3.19）

512 字节以内；它覆盖增量事件和崩溃恢复，不运行照片分析、Blender 或

自动资产绑定批次开始时会固定一份资产库快照，供该批场景共享；实际选中
的模型、材质、碰撞文件和清单会在渲染边界复核。续跑及导出使用新的校验
上下文，导出按场景流式复制并在发布前复核结果，避免同时将所有完整场景

## 0.3.22 恢复与停止可靠性

完成、中断和停止时的最终 `summary.json` 不再被同一轮旧 `run_state.json` 覆盖，避免最终汇总已经提交、状态文件尚未写入时崩溃，恢复页面却显示“运行中”。回归测试用子进程在该写入间隙直接退出，验证读取结果。

旧记录没有统一的单调尝试序号。`result.json` 与 `last_error.json` 修改时间相等时，现优先错误记录，避免把旧成功恢复为当前合格结果；损坏错误记录也会阻止该场景入库。明确较新的成功记录仍需通过完整输入、产物和验收证据校验。恢复仍依赖文件时间与逐文件哈希，大量历史产物的全量核验有 I/O 成本；这些修复不代表已完成万张真实照片的质量和吞吐验收。

## 0.3.23 请求与本地恢复开销

严格 `json_schema` 输出已经由 provider 的结构化响应格式约束，API 请求不再重复发送通用 JSON 输出说明。每个这类请求的提示文本减少 107 个 UTF-8 字节；这不等于固定 token 数或费用降幅，服务端实际计费仍以 `usage` 返回值为准。`json_object` 和纯提示模式仍保留显式 schema/格式说明。

自动资产库批次在批次级快照已验证资产输入后，恢复已验收场景时不再对该场景重复强制读取并哈希同一组资产文件；即将交给 Blender 的实际选中资产仍会在使用边界检查。当前运行内的产物摘要也会按文件身份签名复用；若设备、inode、大小或时间戳发生变化，就重新计算 SHA-256。此缓存只活在当前进程内，不能抵御伪造相同文件身份元数据的恶意修改；续跑入口和正式导出仍会建立新的校验上下文。

这些改动降低重复文本和本地重复 I/O，不证明真实图片 token、端到端耗时或费用按固定比例下降。0.3.23 的完整离线回归为 715 项通过、93 项因需要 Blender Python 跳过；另外，本机 Blender 通过 loopback 模拟 API 完成了 2 项真实构建/渲染集成测试。没有向付费模型发请求。

## 0.3.25 细节提示压缩

计划表编码被自动选用时，非目标构件不再重复发送仅用于细节图像路由的证据视角和置信度字段；目标构件的证据、全部构件的空间/支撑/材料/构造信息及本地原始计划保持完整。只有编码文本连同说明确实更短时才启用。八组、双视角合成计划的细节请求正文减少 340 个 UTF-8 字节；这不是模型 token 数或费用降幅。全套离线回归为 718 项通过、93 项跳过，未调用付费 API，也未验证视觉质量等价。

## 0.3.26 万级批次预算门

实际运行达到 1,000 个场景时，若整批请求数、最大输出 token 或服务端报告 token 任一上限缺失/为零，CLI 会在 provider 与 Blender 预检前停止。`--dry-run` 保持可用，并以固定 20 项预览输出场景/图片总数及缺失限额。额度值由操作者根据账户配额和支出上限设置；预算账本按输出目录记账，不提供跨目录/跨机器全局预算。

## 0.3.27 续跑索引内存

协调器恢复已有结果后，会在建立本次请求的运行状态时释放这些 requested 场景的旧完整记录，避免 artifact 清单在 `records` 与 `current` 中重复驻留。未请求的历史场景仍保留；worker 返回 accepted 前仍独立校验场景结果、artifact 哈希和资产快照。新增恢复生命周期回归，10,000 场景账本压力测试继续通过。该改动降低续跑峰值内存，不改变真实图片重建的 token、耗时、费用或质量结论。

本轮运行中，worker 完成结果先追加到已 `fsync` 的 `batch_events.jsonl`，协调器的热状态只保留场景 ID、目录和状态。终端 `summary.json` 与 `accepted.json` 会从本轮事件恢复完整结果，因此 artifact、审核历史和 gate 字段的兼容格式不变。恢复入口对本次 requested 场景跳过重复的旧索引扫描；`run_job` 返回 accepted 前仍执行权威结果、产物、源照片和资产快照校验。事件日志仍会随场景数增长，真实 Blender 进程内存和磁盘峰值需要按实际资产与渲染参数测量。


## 0.3.28 发布边界

0.3.28 包含上一节描述的事件日志和终端快照恢复路径，以及对应的离线回归。打包前应重新记录完整测试数量、跳过数量、wheel SHA-256 和隔离环境中的 CLI 版本，不能沿用 0.3.27 的验证文件。用真实 `atomic_json` 写入路径做的 10,000 条合成提交测得事件日志约 32.6 MB、终端汇总约 35.1 MB，进程峰值 RSS 约 131.4 MiB；另一条为断言而序列化完整快照的测试工具测得的更高峰值不代表协调器运行内存。事件日志、恢复索引和预算账本已通过合成大批次压力测试；这不等于真实照片、付费模型请求或 10,000 个 Blender 场景已经生产验收。

## 0.3.29 细节请求压缩回归

稀疏细节响应模式现在只使用稀疏字段说明，不再同时附带完整数组格式的冲突指令；原有局部坐标、房间边界、支撑和材料约束保持不变。对五条已保存的 GLM 办公室细节调用（132 个部件）做离线重放，提示词、schema 和响应合计从 77,757 字节降至 74,782 字节，减少 2,975 字节（3.83%）。这是 UTF-8 序列化大小，不是服务商 token 或费用测量；没有发送 API 请求，也没有验证视觉等价。该模式仍需显式启用，默认保持兼容格式。

0.3.29 完整离线回归为 821 项：728 项通过、93 项因测试环境缺少 Blender Python 而跳过，0 项失败。10,000 场景调度、预算账本、分页报告和流式导出证据来自合成/mock 数据。它们验证本地批处理与账务基础，不证明真实照片重建能在万级规模下按期、按预算或按目标质量完成。真实照片 API/Blender 试产、通过率、端到端速度、图像质量和实际费用尚未验证。

## 0.3.30 Blender 缓存与万级检查点

复用办公室资产时，如果 Blender 已加载或清空场景，模块级缓存可能仍指向已删除的数据块。细节资产现会验证 Blender 是否仍拥有缓存的网格和材质，必要时重建。Blender 5.2 LTS 当前环境中直接运行的 94 项专项回归全部通过，其中包括实际 Cycles 渲染；普通 Python 回归为 822 项，728 项通过、94 项因普通解释器没有 Blender Python 而跳过。普通回归覆盖其余几何、API 与批处理测试。

终端汇总现在将当前场景状态和已落盘的事件结果逐条并入同一恢复索引，保持当前状态与事件提交的优先级，并保留原有摘要顺序。10,000 个合成场景提交重跑约 5.5 秒，事件日志 32,608,894 字节，运行时状态最高 280 字节。单次带测试观测的 macOS 协调器进程峰值 RSS 约 395 MB；测试序列化结果、操作系统缓存等会影响该数值，不可据此推算 Blender/API 生产内存。真实照片分析、付费 API、万级渲染吞吐和验收率仍未验证。

在进行真实扩量前，仍需用代表性的输入执行 100、1,000 和目标规模的分阶段试产，并保存 API token/费用、渲染耗时、磁盘峰值、Blender 内存、验收通过率和失败分类。只有最终验收通过且完整性复核成功的场景才可由 `export` 发布。

## 0.3.31 限流等待与资产导出

API 保留服务端 `Retry-After` 的最短等待时间，不再把较长的等待缩短到 30 秒。等待超出本次请求的剩余时限时直接结束，不提前重发；同一服务的批次冷却时间也不再缩短。批次停止可立即唤醒重试等待，已发生的请求仍保留审计与预算结算，不虚构退款。已发送且结果不明的请求继续禁止自动重放。

连续导出使用同一资产目录的场景时，只解析一次源资产目录。缓存仅存在于当前导出，最多保留一个目录；每次复用检查路径和文件身份，发生变化时重新读取并核对已提交的摘要。切换目录或开始下一次导出会重新加载。逐场景资产、贴图和复制完整性校验，以及发布前的新一轮完整验证继续执行。两场景真实导出夹具验证完整目录加载由两次变为一次；这不是万级真实导出耗时的测量。

协调器用集合判断已请求的场景，保留原请求顺序，消除这一步对列表的重复线性查找。本版只调整本地调度、限流与导出，不改变原图分辨率、重建提示词、渲染或验收标准；没有新增付费 API 试产或视觉质量结论。升级后请使用新的输出目录，保留原结果。

## 0.3.32 本地诊断与资产快照缩放

`usage` 现在一次遍历批次目录，同时发现 API 调用记录和场景预算账本，并明确不跟随目录符号链接。API 记录逐条发现、读取和汇总，不保留所有 API 路径；预算路径仍保留并排序。10,000 场景合成夹具中，目录扫描从 80,004 次降至 20,001 次，用时从 1.711 秒降至 0.853 秒，完整统计结果一致。此夹具的报表 Python 峰值分配从约 5.42 MB 降至 2.17 MB；没有测量预算记录列表负载。这些单样本仅测量本地报表发现和 Python 内存，不代表 Blender/API 生产速度或整个进程内存。

网页对比优先用批次摘要中已保存的视角路径，避免每个场景都解码完整几何参数文件；旧批次继续从场景 JSON 读取视角。它仍是未验证的展示用途，不是验收证据，正式导出仍独立校验逐场景状态和文件哈希。在两个版本处理同一份 10,000 场景合成目录的对照中，旧报表读取 10,000 份、合计 531,720,000 字节的场景 JSON，新路径读取 0 份；时间为 4.21 秒和 3.23 秒，200 页网页与拼图 SHA-256 完全一致。这些是硬链接/合成元数据上的单机报表测试，不是场景重建或照片质量结果。

预算只读快照在一次原子文件读取中校验并生成结果，避免在并发账本替换时混合两个版本的策略和计数。资产库快照验证也去除了每个现存文件上重复的一次完整路径符号链接检查；缺失文件仍检查所有路径组件，现存文件依旧由稳定身份校验执行该检查。所有回归均检查变化拒绝和不读取链接目录。

本版只优化本地报表和文件系统检查，不改场景生成、图片分辨率、模型请求或验收门槛；没有调用付费 API，也没有视觉质量测量。万级模型调用、Blender 渲染吞吐、峰值显存/内存、真实 token 费用和验收通过率仍未验证。


## 0.3.34 省成本配置启用稀疏细节传输

`bigmodel-production-cost-saving` 现在在已有高置信度细节视角路由之外启用
`native_sparse_parts_v1`。该编码只省略与当前 primitive 无关的空数组，并把曲线、网格和布帘的真实拓扑按部件索引传输；解码后恢复 canonical 字段，再走完整细节、场景和 Blender 校验。质量优先配置仍使用 canonical wire。离线历史回放显示 132 个部件的 prompt/schema/响应 UTF-8 字节减少 3.83%，但这是序列化代理指标，不是 provider token、费用或视觉等价证明。

## 0.3.35 按构件范围传递贴图证据

启用 `pipeline.staged.route_detail_images=true` 时，规划结果为每个构件组声明几何证据视角、照片贴图材质清单及对应置信度。达到门槛后，细节请求只携带该组的证据视角和所需贴图源视角；动态 schema 同时限制可用的照片贴图材质，避免模型引用未收到来源图的材质。映射缺失、低置信度、不一致或组未观测时，程序回退到全部原图。路径默认关闭，质量优先配置保持全图；成本配置显式开启高门槛。

该修改不会缩放原图，不会改变相机或场景几何。离线集成测试验证附件路由、白名单、缓存隔离和来源记录，但没有真实 API 视觉等价或计费测量。模型自报置信度并未校准，因此不能把合成附件数减少当成真实质量或 token 节省证明；切换正式数据集前仍需代表性照片验收。

## 0.3.33 局部计划修补与可行光照回退

完整计划已返回且通过原始 JSON、schema、输入照片和 API 来源核验后，如果唯一失败类别是基础资产的旋转后边界越界，后续验证重试改为绑定原候选 SHA-256 的数值补丁。可修改的范围只有被本地几何检测指出的资产位置、尺寸、旋转和重复间距；资产 ID、数量、类别、材质、相机、房间和全部自定义组保留。补丁合并到原计划后仍运行完整验证，成功后才开始细节调用，不做自动坐标夹紧。相机、组锚点等混合或全局错误仍走完整计划重试。原重试次数、预算和不确定请求重放保护继续适用，原图及所有视角保持不变。

失败草稿、补丁输入、补丁响应和合并后的 canonical JSON 分别留档并校验哈希；恢复运行可重用已验证修补结果，拒绝被修改的候选。新辅助模块同时纳入分析和外层批次代码指纹。升级需新输出目录，不会改写历史结果。减少整份计划的重复输出不等于已实测的 token/费用降幅：补丁请求需要带回完整草稿，输入可能变长，实际收益仍需服务商用量对照。

灯光边界保护拒绝最优提案后，程序先检查已经渲染过的其他候选。只有所有功率和曝光未触边、相对原始场景的空间亮度损失至少下降 2%、且每个视角均不退步的候选才可保留；否则恢复原始设置。此步骤不额外渲染候选、不调用模型。存在严重残差时仍记录未解决状态，不能视为通过验收。最终九格诊断现会单独报告任一有效区域超过 2 stops 的误差，避免被中位数或分位差隐藏。

本版是在本地回放、模拟 API 和 Blender 验证范围内推进。真实模型的补丁质量、真实 token 消耗和万级照片生产通过率尚未完成付费试产验证。原图分辨率与仅导出独立验收通过场景的要求保持不变。

## 0.3.37 本地请求载荷观测与磁盘准入

`usage` 报告新增本地请求载荷指标：序列化请求 JSON 字节、各张原图的文件字节数/Base64 字节数/像素尺寸、响应字节和提取后的输出字节。指标明确标注为本地传输大小，不换算成 provider token、图片 token 或费用；真实计费仍采用接口实际返回的用量数据。

`batch.min_free_disk_bytes` 增加启动前和每个新场景开始前的磁盘余量检查。磁盘不足时暂停新任务，已开始的 API/Blender 工作完成后保留检查点；空间恢复后可继续处理 pending 场景。它不能阻止正在运行的场景继续写入，也不会估算最终所需空间。

`batch.shared_ledger_dir` 允许同一台机器上的多个输出分片共用批次预算和供应商限流 SQLite 账本。输出目录必须位于该共享根目录内；每个分片仍有自己的输出锁和索引。协调器会在共享分片仍持有其输出锁时允许其他分片加入，但崩溃后释放锁的未结算请求继续阻止恢复，避免把结果不明的请求当作未发送。该机制只协调本机可靠文件锁，不证明多机文件系统或真实服务商吞吐安全。

普通 Python 全量回归为 887 项通过、94 项因 `bpy` 不可用而跳过、0 项失败。10,000 场景模拟只测得本机协调器/索引/预算记账能力；真实照片的 API 成功率、Blender 万级吞吐、真实 token/费用和合格率尚未验证。

工作树续跑修复：如果已完成的 API 响应因后续本地校验失败而需要恢复，而预算账本在 POST 前阻止新的请求，程序保留该阶段原先成功响应的 `.api.json` 用量记录；批次失败原因仍写入场景错误和批次账本。这样本地拒绝的重试不会抹掉已发生的供应商用量。回归测试覆盖“第一次请求成功，第二次因批次上限而未发送”的情况。此修复仍在当前源码工作树中，尚未重新打包到 wheel。

## 0.3.38 共享分片账本

`batch.shared_ledger_dir` 现在可把多个本机输出分片绑定到同一批次预算和供应商限流账本。每个分片必须位于共享根目录内并使用独立输出目录；跨进程 SQLite 事务合并请求数、输出上限、已报告用量和端点 RPM/TPM。正在运行的其他分片持有输出锁时允许加入；崩溃释放锁后，未结算请求仍保持结果不明并阻止恢复。跨进程预算、RPM 和并发待结算请求均有离线回归；这不等于真实服务商吞吐、Blender 渲染速度或视觉质量已验证。10,000 次预算预留/结算在本机模拟约 3.2 秒；10,000 条结果提交约 4.9 秒并产生约 32.6 MB 增量事件日志。测试使用模拟工作，不包含 API 或 Blender。

## 0.3.39 预算阻止后的 API provenance

恢复已完成 API 阶段时，如果新的尝试在 POST 前被批次或场景预算拒绝，保留该阶段先前已完成请求的 `.api.json` 用量和响应记录。预算阻止仍写入场景错误和批次账本，不会发出第二个请求；usage 报表不会因未发送的本地重试而丢失第一次真实调用的数据。离线回归验证了“第一次成功、第二次预算拒绝”时只发出一个 HTTP 请求且首个 API provenance 仍完整。
